## Operator instruction — 2026-09-19: keep sweep point counts modest

- Device/project: `as-qpu-10qV2_agent`
- Operator diagnosis of run `cb707ffb5c1843dfb2c12745e82c24c3`: this timeout was
  NOT an instrument fault. The program simply carried too many sweep points, so
  transfer and compilation had not finished when the 100 s queue-submission
  deadline elapsed. The earlier 02a timeout had a different cause (a genuine
  instrument-side problem).
- Instruction: keep the number of measurement points small. This is mainly
  about the amplitude axis; the number of shots (`num_averages`) has little
  effect on program size, so it does not need to be cut.
- Applied: the 04 default `amp_factor_step` is raised from `0.01` to `0.02`,
  halving a 0..1.7 sweep from 171 to 86 amplitude points. When a run still
  times out during submission, coarsen the amplitude step further before
  touching averages.
- This principle applies to any node whose program size is dominated by a
  swept axis, not only 04.

  the lever is its readout contrast (02c readout amplitude/frequency), not more
  averaging.

## Lesson — 2026-09-20: q1's calibrated x180 never reached state.json

- Observation: q1 cleared the SNR floor in `#164`, but that run also contained
  q2, so the analysis was `needs_review` and 04 suppressed every state update.
  Once q1 was marked resolved, the server refused a further 04 run ("All active
  04 targets are already resolved or incomplete"), so there was no way to
  obtain a pass-backed commit for it. q1 therefore keeps its pre-run x180
  amplitude `0.0364876450` instead of the fitted `0.0367134569` — a 0.6 percent
  difference, Pi factor 1.006.
- Recovery: when a target is expected to need extra averaging, run it alone
  from the start so its passing run is not spoiled by a batch mate. This is the
  same partial-pass commit gap recorded for 02c and 03a.
- Do not copy this as an accepted setting.
